Q3backend development

I want to make sure I understand your implementation correctly. You said you generate the idempotency key after receiving the request on the backend. But if the key is generated server-side for each incoming request, how would two duplicate requests end up with the same idempotency key? Wouldn't each request generate a different key?

Q4the API contract

I think there's a logical issue with what you're describing. If the backend generates a new idempotency key for each incoming request, then duplicate requests would each get a different key, and your conditional write wouldn't help - they'd all succeed because they'd all have different keys. For idempotency to work, duplicate requests need to arrive with the same key. So where does the idempotency key actually come from in your implementation? What are the inputs you use to generate it, and who generates it - the client or the server?

Q5the data layer

That makes much more sense - deriving the key from a stable identifier like the transaction ID. Now let's talk about the conditional write itself. What database were you using for this, and what specific database operation or feature did you use to implement the conditional write? And after the conditional write succeeds for the first request, walk me through what happens next - how do you ensure the first request completes the payment processing, stores the result, and how do subsequent duplicate requests retrieve that result instead of processing again?

The carry-over row went the wrong way, and it is published as it came out. This rung changes exactly one thing against the baseline — the scheduler picks the topic — and the model is still handed the whole transcript to write the wording with, so it still reaches for the candidate's vocabulary. And read the last row beside coverage. The solution covered more competencies in fewer questions, and that is the direction the respondent cannot explain.
changelog

The change that mattered, and the one that was removed

biggest contributor

The scheduler — 60 lines that never read an answer

decide_next() takes the frozen competency plan and the clock and returns the next action. There is no parameter for the transcript, so tunneling is not discouraged — it is unrepresentable. Everything else on the ladder refines a guarantee this one function already makes.

removed experiment

The keyword labeller — deleted after measuring it

Coverage was meant to be resolved by matching slot keywords first, with a model judge only for the hard cases. Over the real baseline run it resolved 0 of 11 questions and mislabelled two: React Query decomposes into react + query, and query belongs to the data layer, so two purely frontend questions read as reaching into it. Deleted rather than kept as decoration.

What deleting it taught, and it cost a published number. The cause was structural, not a keyword needing a tweak: api_contract and cross_boundary_debugging are relational competencies, defined in the other competencies' vocabulary, and no word-matcher separates a question about the boundary from one that merely names both sides of it. The same audit found the carry-over guardrail counting backend, api and request as drift — reporting 100% on the baseline while missing the five consecutive questions about one idempotency key. Corrected to 18%, and both numbers are published.
stated plainly

What this report does not show

I pre-registered the prediction that the baseline would cover ≤2/6. It covered 5/6, and that is recorded as a failed prediction rather than reworded. Coverage is also not a stable measurement — three runs of the judge over the same record returned 5/6, 5/6 and 4/6, which is why the number carrying the argument here is longest_chain, where no model is involved. This is one candidate, one role, one model: every interview costs a human 25 minutes, which is the honest reason there are two of them and not twenty. And two further layers — hiding the transcript, and a checker that verifies each question before it is asked — are built and tested but not yet sat, so nothing here claims them.
